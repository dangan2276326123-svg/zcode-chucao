## 0A. 每次开机：两条命令（09-28 定稿；工具改过一版，旧版列的四步已合进去）

**先做一次**（只在 `vehicle/` 或 `common/` 变过之后要重做；笔记本 Git Bash 里）：

    scp vehicle/start_bridge.sh sunrise@192.168.127.10:~/qoder/vehicle/

**之后每次就这两条**：

1. **X5**：`sh ~/qoder/vehicle/start_bridge.sh`
   脚本里就三行：`pkill -f "cat /dev/ttyS"`（清掉跟 bridge 同读一个串口、把帧撕成半截的人）
   → `cd` 到 `vehicle/`（`config.yaml` 在这儿）→ `exec sudo python3 bridge.py`。
   **必须 sudo**：普通用户开不了 `/dev/ttyS1`，09-28 实测不带 sudo 就是 PermissionError 退出，
   而它一退，笔记本那边看到的是一帧都没有——长得和接线断了完全一样。
   凭证只有一行：`bridge up: udp:9000 -> /dev/ttyS1`，没看见就是没起来。
2. **笔记本**：`python -B tools/bench_status.py`，跑**满 60 秒**再 Ctrl-C，读最后那行**判定**。
   工具现在自己做了三件原来靠人做的判断（09-28 加，都是当天在现场踩过才写进去的）：
   - 启动时核对"本机到底有没有 `vehicle/config.yaml` 里那个 `pc_ip`"——不是就直接说该怎么改，
     不用再自己翻 `ipconfig` 对照；
   - 9100 独占绑定，被人占着就拒启并点名最可能的占用者（`pc/main.py --live` 也绑这个端口）；
   - Ctrl-C 后把计数器翻译成判据：`一行都没收到`→先查发送端而不是拆线；
     `出现过 N 次"重启重同步"`→**板子在复位**（Hw-26），本轮任何模式/动作观察都不作数，
     第一件事是拔遥控接收机供电（Hw-27）；`帧率低于 18/s`→去看 CSV 的 gap 行；
     只有 `✓ 链路稳定` 才允许做场景实验。

**顺手但别省**：每改一次接线，就在记录器窗口敲一行说明 + 回车——它带时间戳落进同一个 CSV，
今天所有"事后想不起当时接了哪几根"都是靠这个补上的。

**不用重做（在设备/系统里，断电不丢）**：X5 `eth0` 静态 192.168.127.10；X5 上 `~/qoder`
那份代码（只在我改了 `vehicle/` 或 `common/` 后要重新 scp，改 `tools/`、`pc/` 是笔记本侧）；
`config.yaml`（`serial_dev: /dev/ttyS1`、`pc_ip: 192.168.127.100` 已是仓库里的正确值，本文
第 3 步"要改配置"正常情况下不用动手）；已烧录的固件（只有重编译过才要重新 Download）。

**故意没简化的一条**：bridge 不做开机自启。它是那条**能往大板发指令**的通道，宁可人手点一下、
看得见 `bridge up` 那行，也不要一个没人盯着却在跑的发送端。这是安全口径，不是偷懒。

**待确认（别当已核实）**：X5 **断电重开**后 `/dev/ttyS1` 还在不在（今天一直是同一轮上电，
没验过重开；下次开机顺手 `ls -l /dev/ttyS*` 记一次）；`sudo usermod -aG dialout sunrise`
+ 重新登录能不能省掉每次 sudo（**未在本机验证**，成了就把上面"必须 sudo"改掉）；
`vehicle/start_bridge.sh` 在 X5 上**还没实跑过**（我这边没有 X5 访问），下次由你验一次；

## 3. UART 自发自收（E2.2 第 4 项提前做，X5 单板即可验）

1. SSH 后装 pyserial：`sudo apt update && sudo apt install -y python3-serial`
2. 列串口：`ls /dev/ttyS*`；`dmesg | grep -i ttyS` 看哪个对应 40pin UART1（预期 `/dev/ttyS1`，Pin8/10）。
3. 若串口被 console 占用或无设备：`sudo srpi-config` → Interface/40pin 复用里启用 UART（以菜单实际项为准）。
4. **短接 Pin8 与 Pin10**（杜邦线），跑：

```bash
python3 - <<'EOF'
import serial
ser = serial.Serial('/dev/ttyS1', 115200, timeout=1)
ser.write(b'PING123')
print('rx:', ser.read(7))
EOF
```

**验收**：打印 `rx: b'PING123'`。

## 4A. E3 台架纪律（2026-10-09 加，批 1b 收口时写）

> **这一节是给站在板子旁边的人看的**，不是设计文档。各条纪律的出处：E3 契约 §8（A12「不改厂商 `main.c`」定案后写进操作规程的那两条）、台账 Fw-18 / Fw-22 / Fw-14 / Pc-9 / Pc-8、`tools/bench_limits.py`；第 7 条的出处是 F1 那条链（`pc/state_machine.py` → `pc/wire.py` → `firmware/retrofit.c:102`，2026-10-10 逐环读码核过）；第 8/9 条 = E3 契约 §5.2（L2.5）与 §6（档案握手）；第 10 条 = E3 契约 §3.2 的 `loop_alive` 与台账 Fw-21；**第 11 条 = 10-10 作者改判（契约 §4.3 重写后的"撤销路径"与台账 Fw-19 的改判分句，第 1/4 条的相应订正同源）**。第 7-11 条那几句"读码核过"的口径都是**编码层**（四态里的第二条），**没有一项在台架上验过**——尤其第 11 条里 `[M]` 那条撤销路径，**往返时延是待测量**（批 1a 计划 Task 9 新加的判据）。
> ⚠️ 今天（批 1a 未烧）板子上跑的还是旧固件：**一条 NAV 就是进 AUTO 的钥匙**，而 `TYPE_MODE` 在它的 switch 里没有分支（`retrofit.c:60-75`）。

1. **停车不要用油门杆**（Fw-22）。`main.c:305` 的 `while(sbus_channel[4]<800 && regGroup[0]==0)` **每轮都重新判、没有一次性闩锁**（对比 `:329` 那个握手块有 `only_start` 门，走完再不进）。行驶中把油门拉到底 ⇒ 再次掉进死等，而循环体**只清 `veloc[]`、既不写 PWM 也不喂狗** ⇒ 轮子**保持上一次写进 TIM1 的占空比**约 3 秒，直到 IWDG 咬复位才停。所以"一把拉到底"在实车上是 **保持原速 → 整机重启**，不是停车。**要停：用协议的急停帧**（`tools/link_probe.py` 的 `estop`、`pc/main.py` 的 [E] 键；⚠️ `bench_status` 的 `!beat` 是**心跳不是急停**，而心跳在 `mode==AUTO` 时的语义是"把权限交回遥控"）。🔴 **10-10 读码订正（本条原写法有一处会害人的口径）**：`ch[6]` 那一档**不是停车档**——`sbus_channel[6]` 在 `uart4.c` 内共 **9 处**引用（`:458/487/516/544/573/625/676/727` 八处独立 + `:774` 与 `adress==20` 合并那处，**原写"六处"已订正**），全部在 `work_send_control()`（`:441` 起）这一个**工作机构** Modbus 写函数里，低于 1400 只是把写帧数据字节填 `0x000000`"停止工作"⇒ **它掐的是除草/喷药/撒肥那一族机构的使能，不撤 PC 权限、不动四轮速度**；厂商那句 `SW_Stop=0;` 在 `main.c:380` 是**注释行**，而 `SW_Stop` 按台账 Hw-2 **只切 `MOTOR_1` 一路 24V**。⇒ 站在车边想"拨一下 ch[6] 让车停下"是错的，**能停轮的只有急停帧 / `[M]` 交回 / 断电**（详见本清单 §4A 第 11 条）。这条会不会天天咬人取决于一个还没量的数（**B3**：油门最低位的 `ch[4]`），**量之前按"会"处理**。
2. **动轮子之前先把驱动轮架空**（A15；`tools/latency_probe.py` 的 D2 同理）。这也是 PC 侧三个发送器（`link_probe`、`bench_status --to`、`latency_probe`）把 NAV 硬拦在 **0.20 m/s** 的原因——那一个数写在 `tools/bench_limits.py`，三个入口共用。理由不是保守：现固件把命令钳到 ±1.0 m/s（`retrofit.c:98-101`）看着像保护，但斜率 `SLEW_ACC = 0.2 m/s²`（`:140`）意味着一条 0.9 的命令**约 4.5 秒后真的**把一台 2.15 m 宽、带着刀和滑台的机器推到 0.9 m/s。超限的命令是 `[TX REFUSED]`：不发、不消耗序号、不落 CSV。**台架没有执行元件 ⇒ 涉及刀/横移的条目今天最多到"信号级"（PD4/5/6 电平随指令变），验收表上不许勾"通过"**（A18，09-22 已定级）。
3. **上电先拨一下油门杆**（Fw-18，作者 09-30 口述证实："不拨杆就有 2.95 秒的复位周期，拨一下就不复位"）。不拨 ⇒ 主循环卡在 `:305` 永远喂不到 1 秒的 IWDG ⇒ **约 2.95 秒一轮反复复位**；启动握手要穿一个**窄窗口：800 ≤ ch[4] < 1100**（`:305` 要 ≥800 才离开，`:333` 要 <1100 才算"已在最低处"）。**看到这个周期别按"板子坏了"排障**，也别顺手去改厂商的门限（A12）。
4. **批 1a 烧上去以后：🔴 10-10 作者改判，本条整条重写**——原文照录在下面，**现行读法看第二条**。
   - **原句（10-09 写，10-10 作者改判撤销，不抹）**："**批 1a 烧上去以后：现场拨档默认 fail-closed ⇒ 进不了无人是设计，不是 bug**。`FIELD_SW_CALIBRATED = 0`（E3 契约 §4.2 第③条；B2 那张通道表没填之前恒不通过——未标定的阈值绝不能当成"条件满足"）⇒ 申请无人一律回 `reject=0x03`。**所以批 1a 之后第一次上台架，能验的是"被拒"那一类**：`0x01` 档案不符 / `0x02` 遥控不新鲜 / `0x03` 拨档不在允许位 / `0x04` 急停仍锁存 / `0x05` 执行面停摆 / `0x06` 本批未实现（TELEOP）/ `0x08` 门 N 拒落刀，外加"MODE 到了、STATUS 里的 `authority`/`reject` 有没有动"。**要验"真的进无人"那一类（E3 场景 ②③⑧），必须先做完 B2 填表**（发射机自己的通道监视页：读 `ch[7]`/`ch[8]` 的三个位置、确认哪一路是**能自己停住的自锁拨动开关**——点动按钮不行，A4），把门限烧进去、`FIELD_SW_CALIBRATED` 置 1 才有得验。"
   - **10-10 作者改判后的现行读法**：**"现场拨档"这一条判据不实现**（契约 §1 的 A4 作废、§4.2 条件③ 就地标注、§4.3 已重写为"撤销路径"；两句原话「先进遥控控制，pc 确认再进 PC 控制」「可以再加一个 pc 取消变回遥控啊」记在契约文首与台账 Fw-19）。⇒ `FIELD_SW_CALIBRATED`/`FIELD_CH`/三个门限**批 1a 一个都不写进固件**，所以**不存在"因为没标定所以谁都进不了无人"那个默认状态**：申请无人能不能过，看的是**档案握手（①）、遥控新鲜（②）、急停未锁存（④）、执行面活着（⑤）**这四条，被拒时 `reject` 直接告诉你是哪一条（`0x01`/`0x02`/`0x04`/`0x05`），HUD 上读得到。**台架分段随之取消**：⑨⑪⑫ 那三条"被拒"类与 ①②④⑤⑥⑩ 那几条"真进无人"类**一次上台架连着跑**，不必等任何填表。

## 0A. 每次开机：两条命令（09-28 定稿；工具改过一版，旧版列的四步已合进去）

**先做一次**（只在 `vehicle/` 或 `common/` 变过之后要重做；笔记本 Git Bash 里）：

    scp vehicle/start_bridge.sh sunrise@192.168.127.10:~/qoder/vehicle/

**之后每次就这两条**：

1. **X5**：`sh ~/qoder/vehicle/start_bridge.sh`
   脚本里就三行：`pkill -f "cat /dev/ttyS"`（清掉跟 bridge 同读一个串口、把帧撕成半截的人）
   → `cd` 到 `vehicle/`（`config.yaml` 在这儿）→ `exec sudo python3 bridge.py`。
   **必须 sudo**：普通用户开不了 `/dev/ttyS1`，09-28 实测不带 sudo 就是 PermissionError 退出，
   而它一退，笔记本那边看到的是一帧都没有——长得和接线断了完全一样。
   凭证只有一行：`bridge up: udp:9000 -> /dev/ttyS1`，没看见就是没起来。
2. **笔记本**：`python -B tools/bench_status.py`，跑**满 60 秒**再 Ctrl-C，读最后那行**判定**。
   工具现在自己做了三件原来靠人做的判断（09-28 加，都是当天在现场踩过才写进去的）：
   - 启动时核对"本机到底有没有 `vehicle/config.yaml` 里那个 `pc_ip`"——不是就直接说该怎么改，
     不用再自己翻 `ipconfig` 对照；
   - 9100 独占绑定，被人占着就拒启并点名最可能的占用者（`pc/main.py --live` 也绑这个端口）；
   - Ctrl-C 后把计数器翻译成判据：`一行都没收到`→先查发送端而不是拆线；
     `出现过 N 次"重启重同步"`→**板子在复位**（Hw-26），本轮任何模式/动作观察都不作数，
     第一件事是拔遥控接收机供电（Hw-27）；`帧率低于 18/s`→去看 CSV 的 gap 行；
     只有 `✓ 链路稳定` 才允许做场景实验。

**顺手但别省**：每改一次接线，就在记录器窗口敲一行说明 + 回车——它带时间戳落进同一个 CSV，
今天所有"事后想不起当时接了哪几根"都是靠这个补上的。

## 4A. E3 台架纪律（2026-10-09 加，批 1b 收口时写）

> **这一节是给站在板子旁边的人看的**，不是设计文档。三条纪律的出处：E3 契约 §8（A12「不改厂商 `main.c`」定案后写进操作规程的那两条）、台账 Fw-18 / Fw-22 / Fw-14 / Pc-9 / Pc-8、`tools/bench_limits.py`。
> ⚠️ 今天（批 1a 未烧）板子上跑的还是旧固件：**一条 NAV 就是进 AUTO 的钥匙**，而 `TYPE_MODE` 在它的 switch 里没有分支（`retrofit.c:60-75`）。

1. **停车不要用油门杆**（Fw-22）。`main.c:305` 的 `while(sbus_channel[4]<800 && regGroup[0]==0)` **每轮都重新判、没有一次性闩锁**（对比 `:329` 那个握手块有 `only_start` 门，走完再不进）。行驶中把油门拉到底 ⇒ 再次掉进死等，而循环体**只清 `veloc[]`、既不写 PWM 也不喂狗** ⇒ 轮子**保持上一次写进 TIM1 的占空比**约 3 秒，直到 IWDG 咬复位才停。所以"一把拉到底"在实车上是 **保持原速 → 整机重启**，不是停车。**要停：用遥控器的停车/互锁档 `ch[6]`**（`uart4.c` 六处引用，低于 1400 即"停止工作"）**或协议的急停帧**（`tools/link_probe.py` 的 `estop`、`pc/main.py` 的 [E] 键；⚠️ `bench_status` 的 `!beat` 是**心跳不是急停**，而心跳在 `mode==AUTO` 时的语义是"把权限交回遥控"）。这条会不会天天咬人取决于一个还没量的数（**B3**：油门最低位的 `ch[4]`），**量之前按"会"处理**。
2. **动轮子之前先把驱动轮架空**（A15；`tools/latency_probe.py` 的 D2 同理）。这也是 PC 侧三个发送器（`link_probe`、`bench_status --to`、`latency_probe`）把 NAV 硬拦在 **0.20 m/s** 的原因——那一个数写在 `tools/bench_limits.py`，三个入口共用。理由不是保守：现固件把命令钳到 ±1.0 m/s（`retrofit.c:98-101`）看着像保护，但斜率 `SLEW_ACC = 0.2 m/s²`（`:140`）意味着一条 0.9 的命令**约 4.5 秒后真的**把一台 2.15 m 宽、带着刀和滑台的机器推到 0.9 m/s。超限的命令是 `[TX REFUSED]`：不发、不消耗序号、不落 CSV。**台架没有执行元件 ⇒ 涉及刀/横移的条目今天最多到"信号级"（PD4/5/6 电平随指令变），验收表上不许勾"通过"**（A18，09-22 已定级）。
3. **上电先拨一下油门杆**（Fw-18，作者 09-30 口述证实："不拨杆就有 2.95 秒的复位周期，拨一下就不复位"）。不拨 ⇒ 主循环卡在 `:305` 永远喂不到 1 秒的 IWDG ⇒ **约 2.95 秒一轮反复复位**；启动握手要穿一个**窄窗口：800 ≤ ch[4] < 1100**（`:305` 要 ≥800 才离开，`:333` 要 <1100 才算"已在最低处"）。**看到这个周期别按"板子坏了"排障**，也别顺手去改厂商的门限（A12）。
4. **批 1a 烧上去以后：现场拨档默认 fail-closed ⇒ 进不了无人是设计，不是 bug**。`FIELD_SW_CALIBRATED = 0`（E3 契约 §4.2 第③条；B2 那张通道表没填之前恒不通过——未标定的阈值绝不能当成"条件满足"）⇒ 申请无人一律回 `reject=0x03`。**所以批 1a 之后第一次上台架，能验的是"被拒"那一类**：`0x01` 档案不符 / `0x02` 遥控不新鲜 / `0x03` 拨档不在允许位 / `0x04` 急停仍锁存 / `0x05` 执行面停摆 / `0x06` 本批未实现（TELEOP）/ `0x08` 门 N 拒落刀，外加"MODE 到了、STATUS 里的 `authority`/`reject` 有没有动"。**要验"真的进无人"那一类（E3 场景 ②③⑧），必须先做完 B2 填表**（发射机自己的通道监视页：读 `ch[7]`/`ch[8]` 的三个位置、确认哪一路是**能自己停住的自锁拨动开关**——点动按钮不行，A4），把门限烧进去、`FIELD_SW_CALIBRATED` 置 1 才有得验。
5. **你每敲一下都可能让桥自己注一条 ESTOP，而这个锁存只能断电清**（Fw-14 + Pc-9）。`vehicle/bridge.py:24` `LINK_TIMEOUT_MS=500`、`:30` `SEEN_WINDOW_MS=60000`、`:206` `auto_on=True` 是硬编码 ⇒ 只要 60 秒内出现过**一条**真帧（`!beat`/`!auto` 都算，不只是 NAV），此后**任何 500 ms 的 PC 静默**都会让桥往串口注一条 ESTOP；而 `retrofit_clear_estop()` 全工程没有调用点，`!clear` 发的 `MODE(0x10)` 在未烧批 1a 的板上整条被丢 ⇒ **只能把板子断电**。**规程**：单发一条探针之后，**先断电再做下一个动作**；要连续观察就**连续发**（`bench_status --to` 边发边记，或用 `tools/latency_probe.py` 的持停/续发段）。⚠️ 边发边记时，回头在 STATUS 里看到的那条 ESTOP **很可能是你自己敲键的节奏造成的，不是被测机制的反应**——把它写成机制结论就是假证据（`_diagnostics()` 的计数与 `--to` 那条时间轴就是用来分清这两者的）。已知口子 Pc-9：`latency_probe` 的续发节奏由**到达的 STATUS** 驱动，STATUS 断流 ⇒ 续发跟着停 ⇒ 又静默。
6. **跑 `tools/latency_probe.py` 的 D1 之前**：先确认这块板会回显 `MODE`（批 1a 烧上去才有）。在未烧的板上，D1 的每一轮 = 发一条 MODE + 安静等 2 秒（补发就不是一次往返了）⇒ **每一轮都会被桥注一条 ESTOP 并锁存**。这几句由工具的 `estop_caution()` 打在开工那几行上，不用翻源码；同一条打印也说明 D1 与 D2 **必须分开报**（斜坡把百毫秒级链路延迟完全掩盖，论文口径是"链路延迟 = D1；机械响应 ≈ D2 − D1"）。

2. **UART 换线**：拔 USB-TTL，改接 X5 40pin：Pin8(TX)→大板 PC7(RX)、Pin10(RX)→大板 PC6(TX)、Pin6 GND→共地（**3.3V 直连，无需转换**）。
   - ⚠️ **换线前先看这条（09-23 依 `大板.pdf` 厂商装配注重写；撤回我此前转述错的位号）**：
     U7 块有**两条并联支路**——「485: **R15、R16 默认焊接**」与「**R25、R26 默认不焊接** = TTL 直通 T6」。
     作者 09-23 已焊 R25/R26（**选对了路**），但 **R15/R16 还在 ⇒ U7 的 RO 仍挂在 PC7 网络上**，
     并联一条新路不等于旁路旧器件。MAX13487 引脚（PDF 直读）：1 RO / 2 RE# / 3 SHDN# / 4 DI / 5 GND / 6 A / 7 B / 8 VCC。
     **本路线唯一需要的动件 = 拆掉 R15、R16**，拆后 T6 就是纯 TTL，不必再去证明"眼下没撞上"。
     旧文"U7 那路选型 0R 是 R23/R13、两颗都贴着"**位号错了**（R13/R14/R23/R24 属 U8 块）；
     "该系列无 DE/RE"也不准（无 DE，但确有 RE# 与 SHDN#）——见台账 Hw-1。

  ⚠️ **10-09 核对：括号里那个数现在有两个答案**——E3 之前 **14 字节**（v1）、批 1a 之后 **19 字节**（v2，多出 `profile`/`authority`/`loop_alive`/`build_id`/`reject` 五个 u8）。线上整帧字节数 = 载荷 + 9（2 头 + 2 长 + 1 型 + 2 序 + 2 CRC），即 **23 / 28**。`pc/status_rx.py` 已改成**按载荷长度分派**（14 与 19 都收，其它长度才计坏帧，E3 契约 §3.5/A8），所以看到 `bad:` 涨：**先确认板上烧的是哪一版**（批 1a 未开工 ⇒ 今天仍是 14 字节那一版），再谈"真失同步"。这条分派也正是"批 1b 必须先合、批 1a 才能烧"的理由——旧解析器见到 19 字节会把**每一帧**计成坏帧，报警会喊成自家解析器而不是链路。

## 1. 烧录系统（E2.2 第 1 项）

1. 下载镜像：https://archive.d-robotics.cc/downloads/os_images/rdk_x5/ → 选**最新 3.x 版本**（Ubuntu 22.04），下载 `.zip` 并解压出 `.img`。
2. 读卡器插 TF 卡 → **Rufus**（https://rufus.ie）→ 选卡 → 选 img → 写入（DD 模式弹窗选确定）。
3. 卡插 X5 卡槽（弹簧卡座，推到底），接电源开机，等 1-2 分钟。

**验收**：板上 LED 正常（红灯常亮/蓝灯闪烁属正常启动序列，以说明书为准）。

## 2. 网线直连 + SSH（E2.2 第 2 项）

1. PC 网口设静态 IP：`控制面板 → 网络 → 以太网 → IPv4`：
   - IP `192.168.127.100`，掩码 `255.255.255.0`，网关留空

4. 查版本：`cat /etc/version`、`rdkos_info`。

**验收**：SSH 进去，版本 ≥3.0.0。

## 3. UART 自发自收（E2.2 第 4 项提前做，X5 单板即可验）

1. SSH 后装 pyserial：`sudo apt update && sudo apt install -y python3-serial`
2. 列串口：`ls /dev/ttyS*`；`dmesg | grep -i ttyS` 看哪个对应 40pin UART1（预期 `/dev/ttyS1`，Pin8/10）。
3. 若串口被 console 占用或无设备：`sudo srpi-config` → Interface/40pin 复用里启用 UART（以菜单实际项为准）。
4. **短接 Pin8 与 Pin10**（杜邦线），跑：

```bash
python3 - <<'EOF'
import serial
ser = serial.Serial('/dev/ttyS1', 115200, timeout=1)
ser.write(b'PING123')
print('rx:', ser.read(7))
EOF
```

**验收**：打印 `rx: b'PING123'`。
【回填】：

## 5. B7：X5 接入链路（E2.2 第 3 项推流 + UART 换线）

1. **推流验证**（先网线直连）：X5 上 `ls /dev/video*` 确认相机（USB3.0 UVC 相机接 X5 USB3.0 口）→ 跑本仓库 `vehicle/stream_pi.py`：

```bash
# X5 上（repo 传过去：scp -r 或 git clone）
sudo apt install -y gstreamer1.0-tools gstreamer1.0-plugins-{base,good,bad,ugly}
python3 vehicle/stream_pi.py 192.168.127.100
# PC 上（Git Bash）：
gst-launch-1.0 udpsrc port=5000 ! application/x-rtp ! rtph264depay ! avdec_h264 ! autovideosink
```

2. **UART 换线**：拔 USB-TTL，改接 X5 40pin：Pin8(TX)→大板 PC7(RX)、Pin10(RX)→大板 PC6(TX)、Pin6 GND→共地（**3.3V 直连，无需转换**）。
   - ⚠️ **换线前先过这条准入（09-22 现场更新，别再按"拍电阻"当待办了）**：
     U7 那一路的 TTL/485 选型 0R **两颗都贴了**（R23/R13；台账 Hw-1）⇒ 485 支路没被旁路。
     U7 是 MAX13487，该系列无 MCU 控制的 DE/RE（自动换向，手册待核），**未关断时 RO 默认在驱动 PC7**，
     会和 X5 的 TX 对顶。判据与三档处置见 `docs/接线图_v1.md` §7 新增那条，一句话版：
     **只接共地＋X5 TX→大板 PC7 一根线，用第二个 USB-TTL 并到 PC7 上当探针看波形**——
     波形干净就继续，PC7 被顶在 3.3V／0 电平抬到 1~2V 就是打架，别硬上。
     方向不对称可用来对症状：PC6→X5 出得去，X5→PC7 回不来。
   - 另一件仍未闭环：**T7（"下载+串口调试"白 6P）各脚 ↔ PC6/PC7/GND 通断**，决定 X5 接 T7、T6 还是 DR25。
   - **严禁**把这条链路挂到 485 第 1/2 路（A_1/B_1、A_2/B_2，原车轮角编码器在用）。
   - X5 供电走自带电源 / 独立 48→5V Buck，**不要从大板 5_A_V/5_B_V（各 1.5A）取电**（推流+推理峰值会拉垮 5V 轨导致复位）。
3. **改配置**：`vehicle/config.yaml`：`serial_dev: /dev/ttyS1`（以第 3 步实测节点为准）、`pc_ip: 192.168.127.100`（网桥阶段改为 PC 网桥侧 IP）。
4. **跑 bridge**：X5 上 `python3 vehicle/bridge.py`；PC 上 `python pc/main.py --live --pi-ip 192.168.127.10 --no-gui`（先别进 AUTO，看 STATUS 收包：HUD/CSV 出现 mcu_mode/batt_v 即 D7 链路通）。
   - ⚠️ **`pc/main.py --live` 与 `tools/bench_status.py` 都绑 UDP 9100，互斥**（`pc/status_rx.py:19`）。
     要看画面/跑闭环 → 开 main.py；**要做 B2 取证 → 关 main.py，只开记录器**（它把每帧、每次模式跳变、
     每段静默 gap 和你敲的场景标记写进同一张带绝对时间戳的 CSV）。记录器拒启时会点名是谁占着端口。
   - `batt_v`/`current_a` 两列在固件里是占位（`retrofit.c:226` 写死 48.0f），**有值≠测到了**，别看它以为电池链路通了。

**验收**：PC 出实时 720p 图（秒表对比法时延 <100ms）；STATUS 帧经 X5 转发到 PC，rx_good 持续增长、rx_bad=0。

## 6.5 网桥台架验证 ✅（2026-09-11，正式 B8 拉距前的台架结论）

- 配对：O1-5G 网桥一对（AP 192.168.2.1 / 客户端 192.168.2.2，SSID Tenda_YDH，CH157 5GHz，透明网桥已启用，信号 -24/-36dBm，SNR 28-32dB）
- 链路：PC(127.100) ↔ 桥A ~~无线~~ 桥B ↔ X5(127.10)，ping 0% 丢包，RTT 1-4ms
- 推流：TCP MJPEG 1080p30 走桥，28.7-30.5fps，首帧 40ms，端到端 **104-225ms**（5 次秒表同框采样，均值 ~155ms；网线直连基准 90-105ms，桥加约 50ms 均值+抖动）
- 结论：台架通过；视频大帧对无线抖动敏感属预期，**B8 正式验收以控制帧 p95 <50ms 为准**（视频均值 200ms 内即接受）
- 运维教训：X5 eth0 运行态偶发挂死（换链路对端后必现一次），**失联第一步 = 断电重启 X5**（30s 恢复，配置无损）

2. X5 IP 仍为 192.168.127.10，PC 恢复 192.168.127.100，`ping` 通即可。
3. **打流**（田间距离 120m 模拟：先把两台网桥拉开实际作业距离再测）：

```bash
ping -n 100 192.168.127.10        # Windows
# 控制帧打流：pc/main.py --live 跑 10 分钟，看 rx_good/rx_bad 与 latency 列
```

**验收**：丢包 <1%，控制帧 p95 <50ms；**不达标 → 调网桥朝向/信道，直至达标才准进 M2**。
> ⚠️ **测量口径（2026-09-14 复审更正）**：`pc/main.py` run_log 的 `latency` 列计时始于取帧后，测的是**感知处理耗时**，不是控制往返；`rx_good/rx_bad` 也不是丢包分母。控制帧 p95 须用**专用往返打流工具**（发 NAV→收 STATUS 配对计时）单独测；视频同框时延、网络 RTT、控制帧往返、感知耗时**四项分开报**。

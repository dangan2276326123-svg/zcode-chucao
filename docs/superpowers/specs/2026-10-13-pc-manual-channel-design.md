# PC 手操档（TELEOP）与无人（AUTO）拆档 设计

**日期**：2026-10-13　**作者**：qoder（设计），作者 2026-10-13 口头批准形状　**状态**：设计已批准，**未实现**
**上位文档**：`docs/superpowers/specs/2026-10-08-e3-control-authority-design.md`（E3 契约）。本文只改"进档门槛"这一处，不改帧格式、不改 STATUS 字段。

## 0. 边界：本文管什么、不管什么

管：把协议里那个一直空着的 `MODE 0x02`（申请遥操作）填上，让"人在笔记本上给速度、车跟着走"成为一个**与"无人"并列、门槛更窄**的模式。

不管：

- **不管刀能不能动**。手操档**绑定门 N**：进档不查刀，进去之后三路刀钉在提位、任何落刀 `TOOL` 帧照旧拒。要"手操带刀"属于门 F 的事，而门 F 的前置（B5 全项 + 刀控 + 继电器板接入）一件没齐。
- **不管四轮同角平移/真转角**。线上没有转角字段，`NAV` 末尾那个 `flags` 字节固件现在根本不读（见 §11），所以手操的"左右"只能是**差速转向**。
- **不解除任何禁令**。"禁止实车 AUTO""禁止按现有接线文档直接带动力接线"两条**原样生效**（§6 给手操单开一条更小的子准入，不是豁免）。
- **不进论文**。`mode=3` 的日志是调试证据，不作任何能力主张（§7）。

## 1. 决策记录（作者原话，2026-10-13）

| # | 决定 | 依据（作者口述） |
|---|---|---|
| B1 | PC 控车与无人拆成两个模式，**手操的门槛比无人少一道** | 「就是 PC 控制和无人分开，分成两个模式，PC 控制的门比无人的门少一个」 |
| B2 | 少的那一道 = **遥控必须新鲜** | 同一轮澄清；其余三道（档案、急停未锁存、主循环活着）保留 |
| B3 | 手操档**绑门 N**（不管刀、不许落刀） | 「先只要轮子（手操 = 门 N）」 |
| B4 | 限速上限 **0.1 m/s** | 「手操档速度可以改成 0.1」 |
| B5 | 输入 = **笔记本键盘**，且**后退要先实测四轮换向才放开** | 「键盘，但先把后退也一并验了再上」 |
| B6 | 手操期间**不因刀具被挡**——进档条件里不许出现刀 | 「因为现在车上没刀，我就一直进不去 PC 控制」→ 当场读码更正：**现在的进档条件里本来就没有刀这一条**（§3 念原文），故 B6 已被现状满足，本文把它钉成一条不许回退的约束 |

⚠️ **B6 那条更正很重要，别让它漂回去**：作者读文档读出来的"刀挡门"这个心智模型与代码不符——`enter_unmanned()` 查的四个量里没有一个是刀；它对刀做的是**主动钉提位**，不是检查。真正让他"进不去"的是①板上还是旧镜像（`MODE` 帧整条被丢）、②`0x02` 本来就写着未实现、③批 1a 未烧录。

## 2. 两个模式的门槛表

| 门 | 无人 AUTO | 手操 TELEOP | 为什么这么分 |
|---|---|---|---|
| ① 档案握手一致（`handshake_ok` 且 `pc_profile == PROFILE_ID`） | 要 | **要** | 不是审批，是单位：速度值是按"这是哪台车"的档案换算的，档案错了给的速度就错 |
| ② 遥控新鲜（`retrofit_sbus_ok()`） | 要 | **不要** | 这道门保护的是"自主跑时遥控随时能抢回来"；手操时人本来就是指令源，遥控可以不开 |
| ③ 无急停锁存 | 要 | 要 | 刹车状态 |
| ④ 主循环活着（`loop_alive`） | 要 | 要 | 执行面死了就不许交权 |
| ⑤ 刀具许可（门 N/门 F） | 门 N 强制提刀 | **同左** | 手操不新增任何落刀通路 |
| ⑥ 视觉信心 | PC 侧 `confidence_ok`（`[A]` 键路径） | **不适用** | 手操的速度来自人，不来自视觉；把信心判据套到手操上会在台架（没有行墙）永远进不去 |

> ⚠️ **10-14 上午台架读数给这张表加一条前提：② 在这台车上是恒真的。** 遥控器关机后接收机照常发合法 SBUS 帧（`telecontrol.c` 只看"整帧有效"，故意没用 flag 字节 —— 见台账 **Hw-17 / Hw-28**），所以"关遥控"造不出② 失败；实测 `link_probe mode_auto` 一帧就能把车从 TELEOP 推进 AUTO、`reject=0`。⇒ **本表"手操比无人少一道门"这件事在台架上目前不可测**（要拔 SBUS 信号线才行），而它同时说明：**无人档的② 现在不提供任何保护**，一条 UDP 帧 + 档案号对上就能进无人 —— 这正是"禁止实车 AUTO"这条禁令的技术依据，也是 Hw-17 那条 flag 极性实测升级为必还欠账的原因。

**少掉②的代价必须明写在同一张表下面**：手操时"一摸遥控器就能抢回来"这条保底路径**不再成立**，能停它的只剩 `[E]`、链路静默 500 ms 由桥自注急停、以及断电——前两条至今**没有带动力实测过**（§6）。

## 3. 现状（当场读码，2026-10-13；行号会漂，一律附定位命令）

⚠️ **本节写的是"动手之前"的现状**（2026-10-13 上午读码所得）。同日晚些时候 PC 侧与固件侧已按 §8 落地并编译通过，所以这里的四条"还没做"里有三条已经不成立——**留在原处不删，是为了让"当初是按什么事实做的决定"这句话还有据**；实现后的状态记在 §8 末尾与台账 §4。

- 固件进档判定：`retrofit.c` 的 `enter_unmanned()`，四道门依次为 `REJ_PROFILE` / `REJ_RCS_STALE` / `REJ_ESTOP_LATCHED` / `REJ_LOOP_STALLED`，其后紧跟一行 `if (want_mode == MODE_TELEOP) { reject_code = REJ_NOT_IMPL; return 0; }` ⇒ **手操今天被最后一行挡死，且挡死之前它已经查完了无人那四道门**。定位：`grep -n "enter_unmanned\|REJ_NOT_IMPL" firmware/大车proj/大车/HARDWARE/retrofit/retrofit.c`
- 执行面**已经预留**：`retrofit_on_nav_frame()` 存速度那段的判据是 `if (mode == MODE_AUTO || mode == MODE_TELEOP)` ⇒ 批 2 只差"允许进入 + 限速"。定位：`grep -n "MODE_AUTO || mode == MODE_TELEOP" firmware/大车proj/大车/HARDWARE/retrofit/retrofit.c`
- **厂商 `main.c` 两处只认 AUTO**，这是本批最要紧的一处漏洞：转角清零（`if (retrofit_mode() == MODE_AUTO) { angle[0]=angle[1]=angle[2]=angle[3]=0.0; }`）与四轮速度覆盖（同一分支里 `veloc[0]=veloc[2]=vl` 等）都用 `== MODE_AUTO` 判。⇒ **若手操档不改这两处，进 TELEOP 后四个转角仍沿用 `path_plan()` 从遥控通道算出来的旧值**，遥控器没开时那是个没人维护的残值，车会朝你没收的方向拐。定位：`grep -n "retrofit_mode() == MODE_AUTO" firmware/大车proj/大车/USER/main.c`
- PC 侧**完全没有手操位**：`pc/state_machine.py` 只有 `MANUAL/AUTO/LIFT/ESTOP`；`pc/wire.py` 的 `HOLDING = ('AUTO', 'LIFT')`；`pc/main.py` 按键表只有 `a/m/e/r/c/q`（**没有方向键，也没有手操键**）⇒ E3 契约 §7.1 写的"批 1 三件事"中"PC 侧状态机留位"**没做**，本批顺手补平。定位：`grep -n "HOLDING" pc/wire.py`、`grep -n "ord(" pc/main.py`
- `common/protocol.py` 只有 `MODE_REQ_TELEOP = 0x02` 这一个常量孤零零待着。

## 4. 输入层（键盘）

- 键位：`[T]` 进手操；**按住** `W` = 前进，按住 `S`/`D` = 左右差速（直行与转向合并在"两侧轮速"这两个数上）。**不用 `A`**——它已经是"申请无人"，一个键两种含义是明天的事故。
- **松手归零靠超时，不靠松开事件**：每收到一次键就把目标速度与时间戳记下，**100 ms 内没有重复键就立刻发 `NAV(0,0)`**。`cv2.waitKey` 在按住时会重复投递，但"松开"没有可靠事件；把它当存在性判据会让车多走半秒，而那半秒在田间是压苗。
- 每 50 ms 一帧的节奏沿用现有控制循环，**不为手操新起线程**。
- HUD 必须常显"手操目标速度 = x.xx"和 `mode` 的 ASCII 短码，让人一眼看见"现在是谁在说话"；松手归零要在 HUD 上看得见。
- 键位改动只在 GUI 那条路上生效（现有按键处理整段在 `if not args.no_gui:` 里）⇒ **手操档不许用 `--no-gui` 跑**，这条要写进 X5 清单那一格。

## 5. 速度包络：0.1 m/s 落在两层

> **⚠️ 10-13 傍晚改判：上限 0.1 → 0.2（作者当场定），本节下面那几条里的
> "0.1"一律按 0.2 读，原文不删。** 依据是台架真机第一轮：命令层 CSV 里 W 按住连续
> 350 拍都是 `0.100`，**轮子只转了一下、3.25 m 的上代车落地没走** —— 0.1 m/s（每秒 10 cm）
> 在落地带动力下不够起步。改判走的是"先测再定值"之外的另一条：作者选了直接抬，
> **没做**"遥控最低档能不能走"那个免费对照，所以 0.2 这个数目前是**试出来的第一档，
> 不是标定值**（§12 那条"实际轮速偏差"仍然空着，且现在要按 0.2 测）。
> 两层同改：`pc/wire.py:TELEOP_MAX_MPS` 与 `retrofit.h:RETRO_TELEOP_MAX`，只改一层必然无效
> （PC 发 0.2 会被固件钳回 0.1，而 CSV 的 `vL`/`vR` 仍写 0.200 —— 症状是"看起来生效了"）。
> 这条漂不动了：`tests/test_teleop.py::test_teleop_cap_matches_the_firmware_constant`
> 直接读固件头文件比数值。⚠️ 顺带一条：**0.2 正好等于 `tools/bench_limits.py` 那个
> 台架直发闸 `NAV_BENCH_LIMIT_MPS=0.20`**，手操档现在顶在台架允许的上限上，
> 再往上抬就要同时谈那条闸，别默认它无限。

- **PC 侧**：手操路径上钳 `|v| <= 0.1`，且**在 `frames_for_state()` 之前**钳（钳在发帧之后等于没钳）。
- **固件侧**：`TELEOP` 分支里独立钳 0.1。**两层都要**——线来的速度不能假定是谁发的、也不能假定发送方自觉。
- 现有 ±1.0 m/s 的通用钳位**保留不动**（它是 AUTO 的兜底）；`tools/bench_limits.py` 那条 0.20 m/s 是工具的直发闸，与本档无关，不改动它。
- **负速度（后退）分阶段**：第一阶段 PC 与固件都只放 `0 ~ 0.1`，负值钳成 0（**这条钳位本身要有单测钉住**）；等 `docs/四轮行走方向实测表_20260923.md` 填完、四个轮子正反都实测对得上、左右对称性有数之后，再放开 `-0.1 ~ 0.1`。理由不是谨慎，是记录：行走方向的定案已因 MCU 在台架上的复位循环**作废过一次**，而换向是 `pwm_veloc` 的符号加一个继电器切换做的，今天没有凭据。这也跟"那张表没填完之前不许据此改判据"这条既有规矩同向。

**10-13 进度（作者当天填了那张表）**：`docs/四轮行走方向实测表_20260923.md` 已填完，但**测的是上代车、宏=0**，结论是四轮换向对称、**不需要再翻任何一轮**（这同时把 Hw-23 ① 那句"前轮向后"归因清楚：那是宏=1 那版镜像造出来的现象，不是厂商原样下的事实）。⇒ **负速度仍锁在 0**，放开条件从"表填完"收紧为"**样机上按同一张表重跑一遍**"——依据是本仓既有那条"上代车的实测搬到样机（2.15 m）不得继承"（Hw-20/表 §3）。锁的两处分别是 `pc/wire.py:TELEOP_NEGATIVE_LOCKED` 与 `retrofit.c` 里 `cmd_vl/cmd_vr < 0 ⇒ 0` 那两行，放开时**两处一起解、并重编译**。

## 6. 停车与前置实测（这一档唯一欠的硬账，写成准入而不是建议）

砍掉②之后，手操时的停车手段只剩三条：`[E]` 发 `ESTOP` 帧；链路静默 500 ms 由桥自注 `ESTOP`；断电。前两条**至今只到"读代码读到会这样"**。

**子准入（不是豁免）**：

1. **架空轮阶段**：本档可用，无需前置。
2. **带动力阶段**：必须先在**接着动力**的台架上实测并记录两格——(a) 按 `[E]` 到四轮真停住的时间和滑行距离；(b) 拔掉网线之后它是否自停。两格的原始数据进 `results/` 当日目录，读数进台账。
3. **田间**：第 2 条过了才谈，且**人站在车侧、不站车后**；遥控器允许不开（因为②已被拆），但**允许开**——开着它等于免费多一条抢回路径。
4. 这两格没过而把本档带进带动力场景，属于违反本文，且两条硬禁令仍然生效。

## 8b. 落地之后（同日晚些时候；实现层的三件事实）

**做完了什么**：PC 侧（`pc/state_machine.py` 的 TELEOP 态与 `go_teleop()`、`pc/wire.py` 的 `HOLDING`/`TELEOP_MAX_MPS`/`teleop_speeds()`/发帧层钳位、`pc/main.py` 的 `[T]` 与 W/S/D 按住语义）+ 固件侧（`retrofit.c` 进档分档、TELEOP 独立钳位、链路看门狗纳入 TELEOP、持续复查里的遥控失联分档；`main.c` 的转角清零与四轮速度覆盖两处判据）。当场重编译 0 Error，`Code` 与警告数的读数**只写在台账 §4 那一行**（AGENTS 审查清单第 8 条：同一个读数不许抄两处）。

**还没做什么**：未烧录、未上台架、§6 那两格带动力停车实测一格都没做、负速度仍钳在 0、§12 表里的数还空着。**四态只到「已编码 + 已单测 + 已编译」。**

**实现过程中新发现的三件事，都是这份 spec 事前没写对的**：

1. **`main.c` 里不是一处而是六处 AUTO 判据**：除 §3 点名的转角清零与速度覆盖两个 `if`，四条 `send_angle` 里还各藏着一次 `retrofit_mode()==MODE_AUTO?0.0:Switch_direction`。只改两个 `if` 的结果是"轮速听 PC、转角仍叠加遥控档位"——正是 §10 变异清单担心的那种"漏改一处"。落地时六处一起改。
2. **还有第三道隐形的②**：`retrofit_poll_1ms()` 的持续复查里有一条"遥控失联就锁零 + 提刀"，它不分档位。只把进档处的②让开、不改这一条，效果是**车能进手操、但一松遥控器就每一拍被锁零**——门在进档处开了、在复查处还关着。已按档位分开（AUTO 仍查，TELEOP 不查），而链路看门狗反过来**必须**纳入 TELEOP，否则笔记本死掉时没人停车。

## 14. 转向档位：把 NAV 里那个没人读的 flags 字节用起来（10-14 追加，作者"连实现一起做"）

**为什么要有这一节**：作者问"那我怎么转向"。答案分两半，都得写在明面上——
遥控档能转向（`angle[]` 走厂商 `path_plan()`），**手操档不能**，因为 `main.c` 那段门控在
AUTO/TELEOP 下把 `angle[0..3]` 全部清零，而 PC 这条线上**从来没有转角这个量**：
`NAV` 载荷是 `<ffB`（左速 + 右速 + flags），第三字节自批 1a 起就在，**没人读过**。

**本批做完的（可验）**：

| 层 | 做了什么 | 当场凭据 |
|---|---|---|
| 协议 | `flags` 低 2 bit 定义为档位：0 直行 / 1 左 / 2 右 / **3 保留=横移** | `common/protocol.py` 不动（本来就是 9 字节），新增 `REJECT_GEAR = 9` |
| PC | `pc/wire.py` 的 `frames_for_state(..., gear=)` 把档位写进 flags；**不认识或没解锁的档位一律折回直行再发**；`pc/main.py` 加 `g` 键循环 + HUD 显示 + `run_log.csv` 末列 `nav_flags` | `tests/test_teleop_gear.py` 五条（含变异：把 fail-closed 那行改成 `nav_gear = gear`，`test_unknown_and_locked_gears_fail_closed_to_straight` 当场红） |
| 固件 | `retrofit_on_nav_frame` 读 `payload[8]`；`> TELEOP_GEAR_MAX` ⇒ `nav_gear=直行` 且 `reject_code=REJ_GEAR`；STATUS 借 `current_a` 那格回显档位 | 命令行 `-r`：`0 Error(s), 62 Warning(s)`、`Code=45120`（上一版 45104，+16） |

**没做、而且不能顺手做的（下一烧的前置）**：把档位变成四个 `angle[]`。卡在两件事实上，
不是卡在代码量：

1. **"代码下标 0..3 各是哪个物理轮 + 正负号"是未证项**（`docs/四轮行走方向实测表_20260923.md`
   就是为它建的，而 10-13 那次填的是**上代车**、样机不得继承）。在填出来之前给四个角打符号 = 赌。
2. **横移角要按真实轮距/轴距算**：厂商那个 45° 是从 `B_Horizontal=2780 / L_Horizontal=1390`
   推出来的，而实测上代车是 **B=3010 / L=1620**（Hw-20/Hw-23：固件四个几何常数没有一个对得上）
   ⇒ 正确蟹行角约 28°，拿 45° 跑真车就是蹭胎。所以档位 3 现在**两侧都锁死**：PC 不发 3，
   固件收到 3 记 `REJ_GEAR` 并按直行处理。
3. 还有一条范围问题：**门 N 明写禁横移**（PC 与固件各有一份强制 `off=0.0`）。横移属于刀工作的
   门 F 动作，秋季门 N 不需要它 —— 解锁横移 = 改准入门，那是作者的另一笔裁定，不是这段代码。

**这一版烧进去之后能看到什么**：按 `g`，HUD 第二行的 `0.0A` 会跟着变 `1.0A / 2.0A`
（那是借来的回显位，**不是电流**，`RETRO_REPORT_TELEOP_GEAR` 改 0 就还给 `adc_current_a()`）
—— 这一条证明的是 PC → 线上 → 固件 → STATUS 整条回路通。**车还不会因此转向**，
转向要等上面第 1 条填完再烧一次。

### 14c. 2026-10-15 形状订正（作者一句“遥控里的转向是没问题的”触发的反查）

§14b 原文照引不删，其中三条已过期：“转角数值不新算：±20° 是厂商 `path_plan.c:97-110` 自己用过的值”、
“`main.c:529` 说 `angle[2]/[3]` 是后轮，而 `path_plan.c:97-110` 把动那两个下标的那一支标成前轮转向——
两句不可能同时对”、“偏反了就翻那两个符号”。**过期的理由**：`path_plan.c:97-110` 不在遥控的转向通路上——
它受 `sbus_channel[4]<1300` 门控（油门关断＝车停着），跑在 `telecontrol()` 之后；而且它注释里的
“1前轮转向/后轮转向”是旧标签：`control_flag[1]` 按 `:28`／`:163`／`:171` 是**前进/后退**，厂商用它选
“哪根轴领先就打哪根轴”。

活通路（读码，逐条给行号）：`sbus_channel[5]` → `control_flag[3]`，符号约定由厂商自己在 `:243` 写明
“以垂直向前的方向为0度，**左转为正，右转为负**” → `telecontrol():469-526` 按 `control_flag[2]` 选方式 → 
`ackman_steering_front():651-681`：`R=L/tan(direction)`，`angle[0]=atan(2L/(2R-B))`、
`angle[1]=atan(2L/(2R+B))`、`angle[2]=angle[3]=0`。`direction>0`（左）时**两个前角同为正且左前更大**。
⇒ **一个档位一个符号，不是一个轮一个符号**。已落地：`LEFT=(+tg,+tg,0,0)`、`RIGHT=(-tg,-tg,0,0)`；
横移档保持四角同值（厂商斜行 `path_plan.c:920-927` 同形）。

本节仍然欠的只有一次实测，且问题变小了（执行清单新格 **C27**）：这台车上 `+` 是不是真朝左、
动的是前轴还是后轴。`tg` 的**数值**依旧没有依据——`B`/`L` 跟实测对不上（Hw-23），所以两个前角先取等值、
不做 Ackermann 内外差；真 90° 平移要连四轮速度一起重排，而 NAV 载荷只有两个轮速，那是批 2。

`angle[]`；让无人车去读 `control_flag` 等于摇杆给无人车打方向，正是 Hw-28 之后故意把遥控踢出环要防的夺权反演。

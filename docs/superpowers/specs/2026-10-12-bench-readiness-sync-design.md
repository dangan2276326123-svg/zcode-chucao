## 1. 范围与明确不做

**做**：
- 状态文档同步（第 3 节，六处）。
- 三条工具改动 T1/T2/T3（第 4 节），全在 PC 侧与文档侧，**不动 `firmware/`**。
- §4B 对应格的前置栏就地更新（"需补工具"→"可直读，但未台架"）。

**明确不做**（每一条都有理由，不是留着以后再说）：
- **不加 `--force-profile` 命令行旗标**。它原本是为"档案故意配错 → `reject=0x01`"这一格准备的；
  但 `pc/main.py` 与探针的档案号本来就读自 `config/vehicle_profile.yaml`，而该文件的合法值就是
  `profile_id: 1|2` ⇒ **改配置一行 + 重启**即可造出不一致，零新代码路径。
  多一条只在这种场合用的旗标 = 多一个没上台架的怀疑点；而"改配置再改回来"这个动作是可审计的。
- **不做跨进程时间戳自动对齐**。`pc/main.py:223` 与 `tools/bench_status.py` 都独占绑 9100
  （09-22 实测 Windows 上 `SO_REUSEADDR` 会"bind 成功但包只给先绑上的那个"，所以我们故意不用它），
  两边同时开本来就做不到。自动对齐会引入一个新的、未经台架的解释层——
  改用最笨的办法：**跑两遍，两张表都有绝对时间戳，人工对齐**。
- **不改 `main.py` 的握手语义**（`handshake_sent` 一旦置真只在下一次"序号回退判出的 MCU 重启"时补发）。
  它是设计，不是缺陷；需要重放时用探针或重启程序。
- **不动固件、不重编译、不改台账 §4 与 Fw-14/17/21/22、Pc-8 那五行**（批 1a Task 8 已就地改判过）。
- **不预勾任何一格台架结论**。本文与本次全部改动都只到「已编码 / 已文档化」。

## 4. 三条工具改动

**T1 —— 握手与 TELEOP 的入口（原 C10 的旗标方案已否决，见第 1 节）**
- `tools/link_probe.py`：`MODE_REQUEST_KINDS` 增加 `mode_profile`（发 `MODE(0x20)`）与 `mode_teleop`
  （发 `MODE(0x02)`）。两条都**沿用现有那条约束**：档案号只从 `config/vehicle_profile.yaml` 取、
  命令行不接受参数（理由就写在代码注释里——允许手敲档案号等于允许拿另一台车的权限申请无人）。
- `mode_teleop` 的产出是固件回的 `0x06 本批未实现`，它同时证明两件事：MODE 真的进了分派、TELEOP 的
  未实现通路诚实（**不把它写成"TELEOP 可用"**，那是批 2）。
- `tools/bench_status.py`：新增 `!profile`，语义同上，用途是**不重启 `pc/main.py` 也能重放手握手**。
- C10（档案故意不一致 → `0x01`）改为**操作步骤**而非代码：临时把 yaml 改成 `profile_id: 2` →
  重启程序或探针 → 读 `reject=0x01` 且此后 PC 的每条 NAV 都不许让 `authority` 变成 PC 持权 →
  **硬性收尾：改回 `profile_id: 1` 并再握手一次确认**。忘改回的症状会长得完全不像人造成的
  （之后每次开机握手都失败），所以这一步要写进 §4B 该格的正文，不能只写在注释里。

**T2 —— 一列帧型，而不是第三张表**
- `pc/wire.py:RUN_LOG_COLUMNS` **末尾**追加 `tx_frames`，取值 = `wire.frames_for_state()` 那一拍返回的
  帧型串（`NAV+TOOL` / `HB` / `ESTOP` / `-`）。追加在末尾是本表已有的规矩（列表里自己写着"前面各列下标不变，
  按位置读日志的旧消费者不受影响"），本次跟着它做，并用测试钉住。
- `tools/bench_status.py` 不加列：它自己发的帧已经有 `kind=tx_*` 行；缺的只是"PC 做发送方"的记录，那是 `run_log` 的职责。
- §4B 的 C2/C18 判据据此改写为**两遍跑**（第一遍 `pc/main.py` 记 `state` + `tx_frames`，
  第二遍 `bench_status` 记 STATUS 的 `mode`/`authority`/`reject`，人工按绝对时间戳对齐），
  并把"为什么不能同时开"（9100 独占绑定 + 09-22 的 `SO_REUSEADDR` 实测）写进那一格。

**T3 —— 一行输出加一段判据**
- `tools/latency_probe.py` 的 `estop_caution()` 多打一行：在未烧批 1a 的板上，D1 每轮超过 500 毫秒静默 ⇒
  桥自注急停并锁存，而 `MODE(0x10)` 会被现固件整条丢掉 ⇒ **只能断电清**，别指望 `[M]` 或 `!clear` 补救。
- §4B 的 C21 那格前置改成"C11 必须先过"。

## 6. 风险与失效模式（这次改动自身带来的）

1. **工具会伪装成被测机制**：本仓反复出现这个形状（Pc-9：续发节奏由到达的 STATUS 驱动 ⇒ STATUS 一断流，
   测量工具自己就静默，桥替我们注入急停；§4A 第 5 条：你每敲一下都可能让桥自注一条锁存）。
   本次新增的两处（`!profile` 与 `tx_frames`）都在同一族里 ⇒ 交付前必须用"旧数据复现旧结论"的对照核一遍再上板。
2. **改 yaml 忘了改回**：见 T1，写成 §4B 正文里的硬性收尾。
3. **列追加的位置错了**：用测试钉住"前面所有列下标不变"，而不是靠人眼看 diff。
4. **警告数抖动被读成回归**：本批实测同一份源码连编三次警告数在两个值之间抖（差异恒是厂商那条 `uart2.h #1295-D`），
   `Code` 逐字相同 ⇒ 任何"警告数对不对"的判断都要同轮连跑两次以上再比（这条已在台账与 AGENTS 里，别再犯）。
5. **范围膨胀**：本文之外的事（TELEOP 实现、长期延迟按 `seq` 测量、硬线急停、刀控、滑台、B5）属批 2 / 批 3，
   本设计一律不顺手做。

## 0. 边界：这份契约管什么、不管什么

**管**：谁能让车轮、刀具、横移动起来；权限怎么进、怎么出、怎么被抢走；权限状态怎么被笔记本**看见并记录下来**；以及门 N（秋季导航验证）的准入序列。

**不管**：刀控接线（P0-7/H5.4，等继电器板照片）、滑台伺服接线（Hw-12）、B5 安全动作全项实测、NAV2/4WS 帧、训练与标注侧三条（C5）、论文侧三条（C6）。这些在 §14 列为批 2/批 3。

**一条硬约束继承下来**：禁止实车 AUTO、禁止按现有接线文档直接带动力接线。本文不解除它，解除条件仍按 v1.0 §4.1 的门 N / 门 F 分列。

## 2. 模型：两根正交轴 + 一个执行许可位

沿用 **v1.0 §4.3** 的两根轴，**禁止揉成一个枚举**：

| 轴 | 取值 | 只管 |
|---|---|---|
| **控制权限** `mode` | `MANUAL`(0) / `AUTO`(1) / `ESTOP`(2) / `TELEOP`(3，批 2) | 指令源、谁能夺权 |
| **车辆档案** `profile` | `PREV`(1，上代车 3.25 m) / `REAL`(2，样机 2.15 m) | 车宽、轮距、相机几何、刀布置、米↔像素换算 |

**档案轴永不影响权限判定，权限轴永不影响换算参数。**

新增第三样东西，它**不是模式**（A5）：

| 执行许可位 `permit` | 含义 | 谁定 |
|---|---|---|
| `GATE_N`(1) | 只许沿行空跑：**刀强制提、横移强制禁** | **编译期常量，烧进固件**，不由 PC 下发 |
| `GATE_F`(2) | 允许落刀作业与横移 | 同上，换门要重编译 |

**为什么不让 PC 下发许可位**：那样"上位机出错"就等于"可以落刀"。烧进固件的代价是换门要重编译一次，收益是刀的安全不依赖笔记本不出错。开机时把「当前门 + 档案号 + 编译时间戳」用现有 HMI 链路上屏（`tjcstr`，不改协议），作者在车边一眼能核对。

PC 侧状态机（`pc/state_machine.py`）保持四态 `MANUAL / AUTO / LIFT / ESTOP`，与固件 `mode` 的映射见 §5.1——**两边不要求同名**，要求的是"PC 是否持权"与固件的**持权者 `owner`** 一致（`owner` 是固件内部量，不上线；线上的 `authority` 字段是"最近一次权限变迁的原因"，见 §3.2）。

## 3. 协议变更

### 3.1 帧类型

| type | 名称 | 载荷 | 线上字节 | 变化 |
|---|---|---|---|---|
| 1 | NAV | `<ffB` vL, vR, flags | 18 | **语义变**：只给速度，**不再改 mode**；`flags` 保留、必须为 0（本文写明它当前无作用，免得下一个人以为它做事） |
| 2 | ESTOP | 空 | 9 | 不变 |
| 3 | HEARTBEAT | 空 | 9 | 不变（收到即把 AUTO 交回 MANUAL，`retrofit.c:70-73`）；**但 PC 侧在持权期间禁止发它**（A9） |
| 4 | TOOL | `<fB` offset_mm, lift | 14 | **语义变**：只在 PC 持权时被接受；`permit==GATE_N` 时固件**忽略 lift 与 offset**（§4.5） |
| **5** | **MODE**（新增） | `<BB` request, profile | **11** | 权限与握手的唯一入口 |
| 0x10 | STATUS | 见 3.2 | **28**（原 23） | 载荷 14 → **19** 字节 |

`MODE.request` 取值：

| 值 | 含义 |
|---|---|
| `0x00` | 交回人工（PC 主动放权） |
| `0x01` | 申请无人（AUTO） |
| `0x02` | 申请遥操作（TELEOP）——**批 1 固件收到即回 `reject=0x06`（本批未实现）**，这样批 2 不用再改协议 |
| `0x10` | 解除急停（A3 单确认） |
| `0x20` | 档案握手（`profile` 字段有效，请求回显） |

### 3.2 STATUS 载荷（19 字节）

`struct '<fffBBBBBBB'`：

| 偏移 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0 | `speed` | f32 | 四轮平均轮速 m/s（TIM3 霍尔） |
| 4 | `current_a` | f32 | 电机电流（**仍是占位 0**，Fw-4） |
| 8 | `battery_v` | f32 | 电池电压（**仍是占位 48.0**，Fw-5） |
| 12 | `limits` | u8 | PD15/PD10/PD11 限位（极性冲突未决，Fw-13） |
| 13 | `mode` | u8 | 0 MANUAL / 1 AUTO / 2 ESTOP / 3 TELEOP(批2) |
| **14** | **`profile`** | u8 | 固件内置档案号：1=PREV，2=REAL |
| **15** | **`authority`** | u8 | **最近一次权限变迁的原因**（诊断用；"当前谁持权"是固件内部量 `owner` ∈ {`RC`, `PC`, `NONE`}，不上线）：0=上电默认 1=PC 申请获批 2=现场拨档夺权 3=遥控失联保护 4=PC 链路失联急停 5=PC 解除急停 6=PC 主动交回 7=心跳交回。**10-10 改判：`2`（现场拨档夺权）随 §4.2 条件③ 撤销而不再有来源，值保留、不复用；撤销走 `6`（PC 主动交回 = `MODE(0x00)`/`[M]`）与 `7`（心跳交回），详见 §4.3** |
| **16** | **`loop_alive`** | u8 | **主循环迭代计数低字节**（A12a）；PC 判据：连续 5 帧（250 ms）不变 ⇒ 执行面停摆 |
| **17** | **`build_id`** | u8 | `__DATE__ " " __TIME__` 全串字节和 & 0xFF，**每次重编译自动变**，不用人记 |
| **18** | **`reject`** | u8 | 最近一次拒绝的原因码，0=无（见 3.3） |

> ⚠️ **`authority` 的语义我在口述时说过是"当前权限源（遥控/PC 无人/PC 遥操作/急停）"，本文改为"最近一次权限变迁的原因"**。理由：当前权限源已经由 `mode` 表达，重复一遍没有信息量；而 codex 新发现一那个事故（笔记本写着 AUTO、车上其实已交回遥控）**恰恰需要一个"谁把它交回的"字段才能诊断**。这是本文对口述的一处订正，明写在此。

> `build_id` 是 8 位校验和，理论碰撞概率 1/256。兜底：开机同时把完整 `__DATE__ __TIME__` 打到 HMI 屏上，人对屏即可认版。这条解决 09-23 那次「两份 hex 的 Code 都是 44848、字节数都是 130,670，只有文件 mtime 能区分，结果白跑一轮」。

### 3.3 `reject` 原因码

| 值 | 含义 |
|---|---|
| 0x00 | 无拒绝 |
| 0x01 | 档案不符（PC 请求的 profile ≠ 固件内置） |
| 0x02 | 遥控不新鲜（`retrofit_sbus_ok()` 为假） |
| 0x03 | 现场拨档不在"允许无人"位。**🔴 10-10 作者改判：条件③ 不实现 ⇒ 当前固件不会产生这一码；值保留、不复用**（`common/protocol.py:REJECT_FIELD_SWITCH` 与 `pc/wire.py` 的短码 `FIELD-SWITCH` 继续留在协议层，含义变成"协议里保留、当前固件不会上报的原因码"） |
| 0x04 | 急停仍锁存 |
| 0x05 | 执行面停摆（`loop_alive` 连续 5 帧未变，Fw-21 探测） |
| 0x06 | 请求的模式本批未实现（TELEOP） |
| 0x07 | 已被现场夺权，锁存中。**🔴 10-10 同因作废：现场夺权随条件③ 一并撤销 ⇒ 当前固件不会产生这一码；值保留、不复用**（0x03 与 0x07 是同一处的两个阶段，撤销也必须成对写，否则读的人以为还有一条活的夺权路径） |
| 0x08 | 许可位拒绝（`GATE_N` 下请求落刀或横移） |

### 3.4 五处同步（v1.0 §4.3 已警告，本文点名）

改 STATUS/新增 TYPE_MODE 必须同步五处，**漏一处就是 PC 与固件字段错位**：

### 3.5 新旧混跑兼容（A8）

PC 侧解析**按载荷长度分派**：14 B → 旧字段集（新字段一律填 `None`，HUD 显示"—"）；19 B → 全字段；其它长度 → 计坏帧并拒绝。

两条必须的测试：**旧固件帧 + 新 PC**（不得崩、不得把 `limits` 当成 `profile`）、**新固件帧 + 旧 PC**（旧解析器只读前 14 B，多余字节必须被忽略而不是报错）。

**实施顺序由此确定**：批 1b 的"按长度分派"必须**先合入并跑通**，然后才烧批 1a 的固件。反过来做，台架当天就会字段错位。

## 4. 固件侧契约

### 4.1 权威判定落在**执行点**，不落在状态变量上

Fw-21 已查明：权限/状态/刀/横移/STATUS 跑在 TIM6 中断（`retrofit.c:508-513 → :311-335`），四轮 PWM 只在主循环末尾（`main.c:567/570/573/576`，全仓唯一调用点）。所以契约要求：

- 四轮：`main.c` 现有的 `:550-565` 门控块**扩展**为"问一次当前持权者 `owner`"，`owner != PC` 时不得采用 `cmd_vl/cmd_vr`；
- 刀与横移：在 `apply_outputs()` / `stepper_update()` 里同样问一次；
- **三处问的是同一个判定函数**，不允许各自复制一份条件（复制就是下一次不一致的来源）。

### 5.1 状态 → 线上语义（A9 状态优先）

> - **CSV（`run_log.csv` 的 `reject` 列）= 数字码**。它是给事后统计与对账用的，不进人话层。
> - **stdout = 中文长文案的落点**：`tools/link_probe.py` 判到 `reject != 0` 时打印 `REJECT_TEXT` 的整句（并把"这是板子对某条请求的答复、不是链路不通"和"reject 记的是最近一次拒绝、可能来自更早那条请求"一起写出来）；`pc/status_rx.reject_text()` 是同一份文案的 API，但 **`pc/main.py` 的 stdout 今天不打印它**——它只打印 **PC 侧自己拒发**那一类（`AUTO request refused: reason=ESTOP|L2.5|CONF-LOW`，即 §5.2 的进门判据拦下时，不是固件回的码）。⇒ **本节当初要求的"补 stdout 一行"没有实现**（`pc/` 不在本次文档收口的可改面内），差距如实记在这儿：**要在一块板上同时看到"固件为什么拒绝"和"PC 为什么没发"，现在得开 `link_probe` 或读 CSV，不能只看 `main.py` 的输出**。批 2 接线时若要补那一行，判据不变：可见、不是十六进制、不谎报。

## 7. TELEOP（批 2）与延迟自测（A11）

### 7.1 TELEOP

批 1 只做三件事：协议里留 `MODE(0x02)` 与 `mode=3`（固件收到即 `reject=0x06`）、PC 侧状态机留位、契约写死安全条件（MCU 侧 500 ms 看门狗已有 + 人工夺权仍然有效 + **因视野受限必须限速**）。**批 2 才写实现。**

**为什么批 1 几乎不要钱**：单片机侧不需要新状态——它看到的还是"有人在发速度帧"，与无人一样；区别全在 PC 侧（谁算速度、限不限速）。

### 7.2 延迟自测两条（都不改固件）

| | D1 控制链路往返 | D2 指令到轮子真的转 |
|---|---|---|
| 测法 | 记 `t0` = 发 `MODE(0x01)`（申请无人）的时刻；`t1` = 收到第一个 `mode`/`authority` 已变的 STATUS。`t1 - t0`。⚠️ **不能用 NAV 测**——A2 之后 NAV 不再改 `mode`，发它看不到任何回显变化；要出分布就交替发 `MODE(0x01)` / `MODE(0x00)`（申请/交回）重复 ≥30 遍 | 发阶跃 NAV(0.14, 0.14)；`t2` = STATUS 里 `speed` 首次 ≥ 0.05 m/s。`t2 - t0` |
| 用到什么 | 现有字段 | 现有 `speed` 字段（TIM3 霍尔） |
| 分辨率 | ±50 ms（STATUS 20 Hz 量化） | 同 |
| 含什么 | UDP 上行 + 串口 + 固件处理 + 下一次 STATUS 组帧 + 回程 | **D1 的全部 + 斜坡限幅 + PWM + 电机 + 传动 + 轮胎** |
| 对应判据 | **B8 的一票否决**（控制帧往返 p95） | "按键到轮动"的工程口径 |

**两个数必须分开报**：`SLEW_ACC = 0.2 m/s²`（`retrofit.c:140`）意味着 0 → 0.14 m/s 需要 **0.7 秒**，它会把 100 毫秒级的链路延迟完全掩盖。论文里写 **D1 = 链路延迟，D2 − D1 ≈ 机械响应**，不写成一个数。

**两个诚实的限制**：① TIM3 是 16 位计时，脉冲间隔 > 65.536 ms 会取模（评审指出 0.005 m/s 会被算成约 0.01451 m/s）⇒ **低速段 `speed` 不可信**，阈值必须取 ≥0.05 m/s，报告里注明低速段无效；② 手机 60 fps 同框拍屏幕与车轮（误差 1/60 s ≈ 17 ms）**只作一次性交叉核对**，用来验 D2 没有系统性偏差，不当常规手段。

**依赖**：A17 的 `bench_status` 发送能力（否则没法同时发和收）。

## 8. 不改的东西，与由此产生的操作纪律（A12）

**不改**：`main.c:305` 那段死等（`while(sbus_channel[4]<800 && regGroup[0]==0)`）保留原样，两个门限（800 / 1100）一个都不动。作者每次上电手动拨杆。

**由此必须写进操作规程的两条**（Fw-18 / Fw-22，台账已登记）：

1. **上电后先拨一下油门杆**，否则主循环卡在死等里、不喂狗 ⇒ 约 2.95 秒一轮整机重启；且此时轮子那条路（`main.c:567-576`）根本走不到。启动握手要穿过一个**窄窗口**：`:305` 要 `ch[4] ≥ 800` 才离开，`:329/:333` 要 `ch[4] < 1100` 才算"油门在最低处"，即 **800 ≤ ch[4] < 1100**。
2. **停车不要用油门杆**。`:305` 那段死等**没有一次性闩锁**（对比 `:329` 的握手块有 `only_start==0` 门，走完再不进），所以行驶中 `ch[4]` 一旦低于 800 会再次掉进去；循环体里只清 `veloc[]`、**不写 PWM、不喂狗** ⇒ 轮子保持上一次写进 TIM1 的占空比，直到约 3 秒后 IWDG 咬复位才停。**停车用遥控器的停车/互锁档（`ch[6]`，`uart4.c` 内 9 处引用——10-10 复核，原写"六处"已订正，全部在 `work_send_control()` 的工作机构 Modbus 写帧里，低于 1400 即"停止工作"；⚠️ 它掐的是工作机构使能，**不撤 PC 权限、不动四轮速度**，所以 AUTO 之下不能当停车手段用，详见 §4.3 第 3 条）或协议里的急停帧。**

⚠️ 第 2 条**是否天天触发，取决于一个还没量的数**：这台发射机油门最低位的 `ch[4]`（B3）。最低位 ≥800 ⇒ 只在接收机失联/未同步时触发；<800 ⇒ 每次拉到底都触发。**B3 因此从"最好量"升级为"必须量"。**

**厂商那条 UART3/Modbus 通路**（A1）：`regGroup[0]` 不再当权限钥匙。本批**不删厂商代码**（A12 不改 main.c 结构），但契约明写：`regGroup[0]==1` 那条分支**不允许动车轮**——批 1a 里用最小改动实现这一点（在 `main.c:550-565` 的门控块里，非 PC 持权且 `regGroup[0]==1` 时同样把 `veloc[]` 锁零），并在台账 Fw-19 记明"已由契约消解，不是接了第二把钥匙"。
